# Initiative Record Standard v0.1

## 1. Canonical record

An initiative is identified by an immutable system-generated code:

`SI-YYYY-NNNNN`

Example: `SI-2026-00001`.

The code is not reused and is not editable after creation.

## 2. Core record groups

### 2.1 Initiative code
Canonical field: `initiative_code`

Rules:
- generated by system;
- immutable;
- unique;
- human-readable;
- no department code embedded, because employees can move between departments.

### 2.2 Proposer / Department
Canonical fields:
- `submitter_employee_no`
- `department_code`
- optional co-authors in `initiative_participant`

Rules:
- employee and department must come from master data;
- store the department used at submission time as a snapshot;
- do not allow free-text department names.

### 2.3 Current condition / Problem
Canonical fields:
- `problem_summary`
- `problem_detail`
- optional `problem_category_code`
- optional baseline metrics through `initiative_benefit`

Rules:
- `problem_summary`: short statement, max 240 characters;
- `problem_detail`: factual description of current condition;
- quantified baseline is preferred where available;
- do not combine problem and proposed solution in the same field.

### 2.4 Proposed solution
Canonical fields:
- `solution_summary`
- `solution_detail`

Rules:
- `solution_summary`: short statement, max 240 characters;
- `solution_detail`: what changes, where, and how;
- implementation plan can be attached separately.

### 2.5 Expected benefits
Use `initiative_benefit`, not one free-text field.

Each benefit row contains:
- benefit type;
- baseline value;
- target value;
- actual value when verified;
- unit;
- expected economic value;
- actual economic value;
- period;
- calculation method;
- verification note.

This allows one initiative to have several benefit types without mixing units.

### 2.6 Implementation status
Canonical field: `implementation_status_code`.

Initial controlled values follow the current paper form:
- `IDEA` — idea only / not implemented;
- `PILOT` — trial/pilot;
- `IMPLEMENTED` — applied.

Do not use workflow approval status in this field.

### 2.7 Attachments
Use `initiative_attachment`.

Required metadata:
- document type;
- original filename;
- storage key/path;
- MIME type;
- size;
- SHA-256 hash;
- uploaded by;
- uploaded at.

The database stores metadata. File binaries should be stored outside the main relational table.

### 2.8 Manager review
Use `initiative_manager_review`.

Structured fields:
- reviewer;
- decision;
- feasibility comment;
- rejection / request-for-information reason;
- due date;
- review date.

The current process gives the manager 5 working days. The application should calculate and display this deadline.

### 2.9 Council assessment
Use `initiative_council_assessment`.

Structured fields:
- meeting date;
- decision;
- novelty comment;
- feasibility comment;
- assessed economic value;
- recommended reward level;
- council note.

No numeric scoring is defined in the source policy, so v0.1 does not invent one.

### 2.10 Economic value
Economic value must not be stored as text such as `"about 50 million"`.

Canonical fields:
- expected value;
- actual verified value;
- currency;
- value period;
- calculation method;
- evidence;
- verifier and verification date where applicable.

Default currency: `VND`.

Annual reward thresholds should compare against annualized or explicitly annual economic value. One-time values must remain distinguishable from annual values.

## 3. Two separate state dimensions

### 3.1 Workflow status
Tracks approval/administrative progress:
- `DRAFT`
- `SUBMITTED`
- `MANAGER_REVIEW`
- `MANAGER_REJECTED`
- `HRD_REVIEW`
- `COUNCIL_REVIEW`
- `GM_APPROVAL`
- `APPROVED`
- `VERIFICATION`
- `REWARDED`
- `CLOSED`

### 3.2 Implementation status
Tracks actual implementation:
- `IDEA`
- `PILOT`
- `IMPLEMENTED`

These must never be merged into one status field.

## 4. Required master data

Minimum master tables:
- `md_department`
- `md_employee`
- `md_problem_category`
- `md_benefit_type`
- `md_unit`
- `md_value_period`
- `md_implementation_status`
- `md_workflow_status`
- `md_document_type`
- `md_review_decision`
- `md_reward_level`

Master records use stable machine codes and editable display names.

## 5. Master-data ownership

Recommended ownership:
- employees/departments: HR source;
- reward levels: HRD;
- units/value periods: system administration;
- problem/benefit categories: HRD + process owners;
- workflow statuses: application-controlled.

Do not duplicate employee or department names manually if an authoritative HR source exists.

## 6. Reward-rule issue to preserve explicitly

The current reward table contains both:
- a 9,000,000 VND level for implemented initiatives with >=300 million VND/year or equivalent broad/long-term impact;
- a special award of 10,000,000–50,000,000 VND for implemented initiatives with economic value above 300 million VND/year.

These conditions overlap. v0.1 stores them as separate master entries but does not automatically resolve the final award. Final selection remains an approval decision until HRD defines a deterministic rule.

## 7. Minimum validation rules

- title required;
- submitter required and active;
- department required and active;
- problem summary/detail required;
- solution summary/detail required;
- implementation status required;
- at least one expected benefit required before submission;
- numeric economic fields >= 0;
- actual economic value cannot be marked verified without verifier/date;
- manager review must be attributable to one reviewer;
- council reward recommendation must reference `md_reward_level`;
- every workflow status change is written to history;
- no hard delete of submitted initiatives.

## 8. SST rule

The initiative database is the Single Source of Truth for:
- initiative identity;
- current workflow state;
- implementation state;
- official reviews;
- economic valuation;
- reward decision;
- document metadata;
- status history.

Excel/PDF reports are outputs, not authoritative data stores.
